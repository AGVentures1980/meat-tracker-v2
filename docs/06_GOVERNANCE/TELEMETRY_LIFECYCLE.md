## Executive Summary

The BRASA Meat Intelligence OS is not a passive reporting dashboard; it is a **real-time operational telemetry platform**. Every business insight, fraud score, portions-per-guest KPI, and supplier audit generated by the system is the downstream result of physical events captured across restaurant locations. 

To maintain the auditability and operational integrity of the system as it scales, this document maps the **complete lifecycle of the 10 core telemetry streams** that power the BRASA platform. For each telemetry type, this document defines:
1. **Telemetry Origin:** Where the data is physically or programmatically born.
2. **Processing & Ingestion Path:** The code components (controllers, services, workers) that parse, transform, and validate the incoming stream.
3. **Persistence Layer:** The specific database tables (Prisma models) and fields where the data is written.
4. **Governance Impact:** The operational heuristics, security controls, or financial calculations that depend on this stream.
5. **Failure Modes & Resilience Policies:** The fallback mechanisms and error-handling paradigms (fail-open vs. fail-closed) when the stream is corrupted or missing.

Engineers, platform operators, and technical audit teams must use this document to understand the data-chain-of-custody before modifying ingestion pipelines or reporting logic.

## 1. Receiving Telemetry

### 1.1 Telemetry Origin
Receiving telemetry is generated at the physical delivery dock of the restaurant when meat shipments arrive. Store managers or receiving clerks scan barcode labels on incoming protein boxes using hand-held scanner terminals or mobile devices running the BRASA Receiving app.

### 1.2 Processing & Ingestion Path
1. The scanner app posts JSON payloads to `/api/receiving/events`.
2. The request is processed by `BarcodeController.ts` and routed to `ReceivingEngineService.ts` and `InboundService.ts`.
3. The raw weights, GTINs, supplier identities, and box IDs are extracted and verified against open Purchase Orders.

### 1.3 Persistence Layer
Data is persisted in the `ReceivingEvent` model in `schema.prisma`:
- `id` (UUID Primary Key)
- `scanned_barcode` (String)
- `weight` (Float)
- `supplier` (String)
- `status` (String: `APPROVED`, `REVIEW_REQUIRED`, `REJECTED`)
- `company_id` and `store_id` (Tenant Scoping)
- `invoice_id` (Link to financial record)
- Linked dynamically to `InboundLineUnit` for purchase line association.

### 1.4 Governance Impact
This telemetry represents the "gatekeeper" of inventory truth. It establishes the exact weight and count of proteins entering the physical building, directly affecting:
- Baseline starting quantities for weekly inventory cycles.
- Immediate detection of invoice-to-dock weight shortages.
- Immediate block on non-homologated proteins or untrusted suppliers.

### 1.5 Failure Modes & Resilience Policies
- **Offline Dock Operations:** If internet connectivity drops at the dock, the mobile app caches events in client-side storage (`IndexedDB`) with local UUIDs. When network connection is restored, the app pushes the cached events using the original timestamp.
- **Spec Violations:** If box weight is outside spec or supplier is unknown, the event is saved with `status = "REVIEW_REQUIRED"` and flagged for manual review, blocking the box from entering prep inventory until resolved.

## 2. Barcode Scan Telemetry

### 2.1 Telemetry Origin
Born at the moment of scanning a physical label on a box. A laser or camera scanner captures the barcode symbology (typically GS1-128 or EAN-13 format) containing encoded product identifiers, lot codes, serial numbers, and weights.

### 2.2 Processing & Ingestion Path
1. Incoming raw string arrays are passed to `BarcodeParserRouter.parse()` in `LabelDataFusionEngine.ts`.
2. The router evaluates the strings against three distinct parsers sequentially:
   - `GS1_AI` (GS1-128 Parser): Extracts GTIN (AI `01`), weights in lbs (AI `3201`/`3202`) or kg (AI `3101`/`3102`), production date (AI `11`), and serial (AI `21`).
   - `EAN_VARIABLE` (EAN-13 Variable Weight Parser): Extracts 5-digit local product codes and 5-digit variable weights.
   - `SUPPLIER_RULE` (Supplier Custom Parsers): Resolves custom prefixes defined in the database for specific suppliers.
   - `FALLBACK`: Catches unparseable barcodes as `UNKNOWN` symbology.

### 2.3 Persistence Layer
Saved in the `BarcodeDecisionLog`, `BarcodeScanEvent`, and `UnknownBarcodeLog` models:
- `raw_barcode` and `cleaned_barcode` (Strings)
- `selected_parser` (String: `GS1_AI`, `EAN_VARIABLE`, `SUPPLIER_RULE`, `FALLBACK`)
- `confidence_gap` and `scores` (Floats, capturing parser matching strength)
- `reason_code` (String, in case of failure)

### 2.4 Governance Impact
Enforces GS1 and EAN standards to verify supply chain integrity. Ensures that a supplier is not delivering mislabeled, substituted, or tampered boxes. Directly feeds the Fraud Intelligence Engine's conflict detection algorithms.

### 2.5 Failure Modes & Resilience Policies
- **Damaged Barcodes:** If the barcode is unreadable, the system logs the incident in `UnknownBarcodeLog` and falls back to manual entry or OCR image capture. The receiving flow proceeds, but the manual entry triggers a `WEAK_RULE_USAGE` risk factor (+15 fraud score contribution) to prevent systematic bypass of automated scanning rules.

## 3. AI Vision / OCR Telemetry

### 3.1 Telemetry Origin
Generated when a user takes a photo of a physical box label using the BRASA app camera, typically because the barcode is damaged, missing, or has failed validation checks.

### 3.2 Processing & Ingestion Path
1. Images are uploaded to a cloud storage bucket via `/api/vault/files`.
2. The image URL is sent to `OCRExtractionEngine.extract()` inside `LabelDataFusionEngine.ts`.
3. Visual characters are converted to structured metadata (lot number, weight, serial number, print text).
4. The outputs are fused with raw barcode scans via `LabelDataFusionEngine.fuse()`.

### 3.3 Persistence Layer
- Uploaded image file metadata is saved in `VaultFile` (associated with the `store_id` and `company_id`).
- Extracted JSON text data is saved under JSON fields in the `ReceivingEvent` or mapped to audit records.

### 3.4 Governance Impact
Acts as a secondary, independent verification stream. By comparing what is visually printed on the label (OCR) with what is electronically encoded in the barcode, the system detects label-tampering fraud (e.g., re-labeling low-grade meat as premium Picanha).

### 3.5 Failure Modes & Resilience Policies
- **Poor Image Quality / OCR Service Outage:** If the OCR extraction returns low confidence (<0.60 for weight, <0.70 for lot) or the service fails, the system **fails open** for operational continuity (returns empty `{}`). It records a diagnostic warning, but does not block the receiving workflow. The system relies on barcode or manual validation while flagging the lack of OCR data for auditing.

## 4. Compliance & Validation Telemetry

### 4.1 Telemetry Origin
Generated programmatically by the server when checking request headers, authorization tokens, database constraints, or system deadlines.

### 4.2 Processing & Ingestion Path
1. Handled by express middlewares (e.g., `garciaRule.ts` for inventory deadlines) and security layers.
2. Involves `ComplianceEngine.ts` and tenant-isolation scoping blocks throughout all controllers and service files.

### 4.3 Persistence Layer
Audit logs and compliance histories are written to:
- `AuditLog` (Captures user IP, action, table mutated, company_id, old/new value JSONs)
- `AuditLogArchive` (For cold-storage retention)
- `WasteCompliance` (For regulatory/waste compliance records)

### 4.4 Governance Impact
Enforces multi-tenant data isolation by restricting database reads/writes to the active tenant (`company_id`). Gates operational access based on deadlines (e.g., locking edit access to the weekly dashboard if inventory was not submitted on Monday by 11:00 AM).

### 4.5 Failure Modes & Resilience Policies
- **Database Connection Failure during Lockdown Check:** In `garciaRule.ts` L56, if the inventory check query throws an error, the system **fails open** (calls `next()`), allowing the store manager to access the dashboard. This prevents database glitches from locking managers out of the system during peak service.
- **Tenant Scope Check Failures:** If `company_id` is missing, undefined, or mismatches the user's session token, the query **fails closed** (throws a strict 403 Forbidden error), ensuring zero multi-tenant cross-contamination.

## 5. Dine-In Portion Telemetry (Lbs/Guest)

### 5.1 Telemetry Origin
Calculated mathematically by the backend engine at the close of each weekly operational cycle, merging actual protein consumption with guest count covers.

### 5.2 Processing & Ingestion Path
1. Triggered via scheduled job or manual request to `/api/engine/calculate`.
2. Processed by `MeatEngine.ts` sequential execution loop.
3. The engine aggregates total purchased protein, starting inventory, and closing inventory to find net consumption.
4. It isolates OLO delivery protein and applies business rules (bacon ratio, chicken bounds, lamb chop exclusions).
5. The result is divided by dine-in guest counts from the POS.

### 5.3 Persistence Layer
Outputs are written to:
- `MeatUsage` (Stores net consumed weight, ideal weight, variance, and lbs/guest per protein group)
- `PilotDailyAudit` (Tracks daily running totals)

### 5.4 Governance Impact
This is the primary Key Performance Indicator (KPI) for restaurant efficiency and executive review. It determines whether a store is operating within budget, wasting protein, or experiencing inventory shrinkage.

### 5.5 Failure Modes & Resilience Policies
- **Missing Inventory Data:** If a store has not submitted its closing inventory count, the engine cannot run. The calculation is skipped, and the UI flags the week as "UNSUBMITTED," triggering the compliance lockout.
- **Calculation Timeout:** If the sequential execution loops timeout, the system displays the last cached `MeatUsage` record in the database rather than showing empty screens.

## 6. Administrative & Executive Override Telemetry

### 6.1 Telemetry Origin
Generated when an authorized supervisor, store manager, or corporate director manually bypasses a system restriction (e.g., approving a box with out-of-spec weight, or editing a forecast after the Wednesday deadline).

### 6.2 Processing & Ingestion Path
1. The supervisor inputs their credentials and triggers the bypass.
2. The request is processed by `/api/override` endpoints.
3. Handled by `RiskEnforcementEngine.ts` and `FraudIntelligenceEngine.ts`.
4. Extracted metadata includes: supervisor user ID, bypass reason text, timestamp, and target event ID.

### 6.3 Persistence Layer
Recorded directly in the targeted event record and log tables:
- `ReceivingEvent.override_flag = true`
- `ReceivingEvent.supervisor_id` (String)
- `AuditLog` (Stores the audit record of the override action)
- `ProcurementAIFeedback` (For AI suggestion overrides)

### 6.4 Governance Impact
Permits operations to flow during exceptional events (e.g., emergency supplier changes), but explicitly registers a heavy fraud risk contribution (+60 `EXECUTIVE_FORCE_OVERRIDE`) in the Fraud Engine. Excessive overrides trigger the `EXCESSIVE_OVERRIDE_V1` fraud pattern.

### 6.5 Failure Modes & Resilience Policies
- **Missing Override Reason:** If the supervisor does not provide a reason text or the credential validation fails, the override **fails closed** (rejects the transaction). Manual override logic must never fail open.

## 7. Production Yield Telemetry

### 7.1 Telemetry Origin
Generated at the kitchen butcher stations. Prep cooks weigh meat blocks before and after trimming fat, sinew, or bones on calibrated kitchen scales and input the weights into the kitchen display interface.

### 7.2 Processing & Ingestion Path
1. Ingested via `/api/prep/trim` endpoint.
2. Processed by `YieldEngine.ts` and verified against expected yields.
3. If yield is outside normal parameters, the system triggers `AiYieldInsight` to evaluate the cause (e.g., bad cut spec from supplier, poor knife work).

### 7.3 Persistence Layer
Data is saved in:
- `TrimRecordEvent` (Stores input_weight, trim_weight, yield_pct, quarantine_reason, status)
- `AiYieldInsight` (Stores confidence, explanation, recommended action)

### 7.4 Governance Impact
Reveals the performance of the kitchen prep team and the yield quality of suppliers. Enables corporate purchasing to hold suppliers accountable for "fatty" blocks that inflate purchased weight but yield low consumable meat.

### 7.5 Failure Modes & Resilience Policies
- **Out-of-Bounds Yield Entries:** If a yield entry is mathematically impossible (e.g., yield >100% or <30%), the record is written with `status = "QUARANTINED"`. This isolates the data from the week's average yield calculations until a chef or kitchen manager audits the scale or entries.

## 8. Demand Forecasting Telemetry

### 8.1 Telemetry Origin
Generated when store managers enter expected guest counts for the next service week, or generated programmatically using historical trends.

### 8.2 Processing & Ingestion Path
1. Forecasts are submitted through the dashboard to `/api/forecasts`.
2. Processed by `ForecastController.ts` and evaluated by `TripleBaselineService.ts` to compute a confidence score against historical benchmarks.
3. Mapped to weekly food ordering models in the SmartPrep system.

### 8.3 Persistence Layer
Written to:
- `SalesForecast` (Stores forecasted guests, actual guests, lunch/dinner splits)
- `ForecastIntelligenceLog` and `OutletForecastLog` (Tracks editing history and models)

### 8.4 Governance Impact
Drives the SmartPrep purchasing recommendation engine. Forecasts are locked on Wednesday of the preceding week to stabilize supply chain orders.

### 8.5 Failure Modes & Resilience Policies
- **Late or Missing Forecasts:** If a manager fails to submit a forecast before the Wednesday lock, the system **fails open** for purchasing by running the `TripleBaselineService.ts`. The engine aggregates the last 3 similar operational weeks (adjusting for holidays) and generates a synthetic forecast. The forecast is written to `SalesForecast` with a `is_system_generated = true` flag, allowing ordering to proceed while noting the compliance exception.

## 9. Continuous Audit & Sentinel Telemetry

### 9.1 Telemetry Origin
Generated programmatically by continuous background worker jobs that audit inventory records, receiving logs, and POS metrics.

### 9.2 Processing & Ingestion Path
1. Executed via `sentinel.service.ts` or the `PilotSentinelAgent.ts` background queue worker.
2. Scans recent database rows for physical anomalies (e.g., lbs/guest out of bounds, single order size anomalies, ribs unit confusion, systemic supplier variance).

### 9.3 Persistence Layer
Saved in:
- `SystemAlert` (Stores store_id, severity: `INFO`/`WARNING`/`CRITICAL`, source, description, raw_data JSON)
- `PilotDailyAudit` (Stores aggregated daily status metrics)

### 9.4 Governance Impact
Serves as the automated "internal audit" layer. Alerts are visible to District Managers and Corporate Executives, highlighting potential data falsification, operational theft, or systemic vendor weight fraud.

### 9.5 Failure Modes & Resilience Policies
- **Sentinel Queue Crash:** Because the job queue runs on an in-memory mock Redis (see `DEPLOYMENT_REALITY.md`), a server restart drops queued Sentinel runs. To mitigate this, the dashboard provides a manual "Run Sentinel Audit" button for District Managers. The Sentinel process itself is fail-open (never blocks user logins or data entry), and errors are logged directly to the server logs.

## 10. POS / Aloha Integration Telemetry

### 10.1 Telemetry Origin
Generated by the restaurant's Point of Sale (POS) system (e.g., NCR Aloha, Micros, Toast) at the close of every check. Ingests check sales, itemized cover counts, and lunch/dinner guest splits.

### 10.2 Processing & Ingestion Path
1. Raw daily transaction logs or PDF sales reports are posted to `/api/pos/ingest` (either via POS API polling or manual file upload by store managers).
2. Processed by `ReportParserService.ts` and queue workers.
3. Extracted fields include: actual guest count, total net sales, delivery sales, and product mix counts.

### 10.3 Persistence Layer
Written to:
- `Report` (Main POS sales and guest count record)
- `DeliverySale` (Aggregates delivery platform sales)
- Mapped dynamically to calculate actual values in `SalesForecast`.

### 10.4 Governance Impact
Provides the definitive "guest count covers" denominator used to calculate the core lbs/guest metric. Isolates Dine-In volume from Online Ordering (OLO) delivery volume, protecting the primary operational KPIs.

### 10.5 Failure Modes & Resilience Policies
- **POS API Offline / Integration Drop:** If the live POS integration fails to connect, the system flags the store dashboard with a "POS Sync Offline" alert. The system **fails open** by displaying a manual upload interface where the manager can drag-and-drop their POS Redbook PDF or Excel file. The parser extracts the covers from the file to maintain calculations. If no file is uploaded, the system falls back to the forecasted guest counts as a temporary denominator, marking the resulting lbs/guest metric as "ESTIMATED".
